# v0.1.0 Release Prep

Target tag: `v0.1.0`

Status: prepared only. Do not create or push the tag, run the release workflow,
or publish artifacts until the maintainer explicitly approves the release.

## Prepared State

- `cmd/gormes/version.go` reports `0.1.0`.
- `Makefile`, Homebrew fixtures, Nix fixture, website footer, README, and
  release docs use `0.1.0`.
- `CHANGELOG.md` has a `0.1.0` section dated `2026-05-01`.
- Release workflow still only publishes GitHub Releases from `v*` tags.

## Required Gate Before PR

Run from `development` and fix any failure before opening the release PR:

```bash
go test ./... -count=1
go run ./cmd/progress validate
git diff --check
```

## Hard Release Rule

Do not create or push `v0.1.0` unless all of these are true:

- The `development -> main` pull request has merged.
- `main` points at the exact commit intended for the release tag.
- Required CI is green on that exact `main` commit.
- No release workflow is pending, skipped, red, or unknown for that commit.

## Approval-Only Release Steps

After maintainer approval:

```bash
git push origin development
gh pr create --base main --head development --title "release: v0.1.0" --body-file docs/install/v0.1.0-release-prep.md
```

After the PR merges to `main`, maintainer approval is explicit, and required CI
is green on the exact `main` commit:

```bash
git checkout main
git pull --ff-only origin main
gh run list --branch main --commit "$(git rev-parse HEAD)" --limit 5
git tag -a v0.1.0 -m "Release 0.1.0"
git push origin v0.1.0
```

The `Release Binaries` workflow will build seven static archives:

- `linux-amd64`
- `linux-arm64`
- `darwin-amd64`
- `darwin-arm64`
- `windows-amd64`
- `windows-arm64`
- `android-arm64 (Termux)`

Each archive is published with SHA-256 sidecars and SPDX SBOMs. GitHub SBOM and build-provenance attestations are generated for each release archive.
